# Library Management System

Sistem manajemen perpustakaan adalah aplikasi yang memungkinkan pengelolaan buku, peminjaman, dan pengembalian buku di perpustakaan. Sistem ini dirancang untuk membantu staf perpustakaan dalam melacak buku yang dipinjam, mengelola stok buku, dan memudahkan pencatatan peminjaman serta pengembalian buku oleh anggota.

> **Learning this codebase?** Start with **[docs/](docs/README.md)**:
> [architecture](docs/architecture.md) · [learning guide](docs/learning-guide.md) · [naming](docs/naming.md)

## Architecture

Go microservices, each with its own PostgreSQL database. **user-service is the only public
entry point**: it serves the REST/JSON API, checks the JWT, and calls the other services over
gRPC. The REST routes are generated by [grpc-gateway](https://github.com/grpc-ecosystem/grpc-gateway)
from each service's `.proto` file, the same pattern as in
[gRPC with REST and Open APIs](https://grpc.io/blog/coreos/).

```
                         ┌──────────────── user-service :6006 (public) ───────────────┐
client ──REST/JSON+JWT──>│ JWT check ─> grpc-gateway ─┬─gRPC─> user gRPC :6007 ──> user_mst
                         └────────────────────────────┼────────────────────────────────┘
                                                      ├─gRPC─> author-service   :6001 ──> author_mst
                                                      ├─gRPC─> category-service :6003 ──> category_mst
                                                      └─gRPC─> book-service     :6005 ──> book_mst
                                                                    │  gRPC: checks author
                                                                    └─ and categories exist
```

| Service          | Public port   | gRPC (internal) | Database       | DB host port |
|------------------|---------------|-----------------|----------------|--------------|
| user-service     | 6006 (REST)   | 6007            | `user_mst`     | 4014         |
| author-service   | none          | 6001            | `author_mst`   | 4011         |
| category-service | none          | 6003            | `category_mst` | 4012         |
| book-service     | none          | 6005            | `book_mst`     | 4013         |

After verifying the token, the gateway:

- removes the `Authorization` header, so the raw token never reaches the internal services
- passes the caller's identity as gRPC metadata: `x-user-id` and `x-user-role`
- drops any `Grpc-Metadata-*` header from the client, so nobody can fake that identity

The internal gRPC ports trust this metadata, so **they must never be exposed publicly**.
docker-compose publishes only port 6006.

Each service is laid out the same way:

```
main.go              calls cmd.Run()
cmd/server.go        startup, wiring, graceful shutdown
internal/config      database connection and migrations
internal/model       GORM models (tables)
internal/repository  database access (interface + GORM implementation)
internal/handler     gRPC handlers (validation, error mapping)
protobuf/<svc>.proto the API contract; generated Go code in protobuf/<svc>pb/
```

user-service also has `internal/auth` (JWT), `internal/gateway` (REST entry point and JWT
middleware) and `openapi/` (the generated API spec).

## Authentication and roles

| Role     | How you get it                                     | Allowed                         |
|----------|----------------------------------------------------|---------------------------------|
| `member` | `POST /api/register`                               | every `GET`                     |
| `admin`  | created at startup from `ADMIN_EMAIL` / `ADMIN_PASSWORD` | everything                |

Tokens are HS256 JWTs signed with `JWT_SECRET` (at least 32 bytes). They are valid for
`JWT_TTL` (default `24h`). Send them as `Authorization: Bearer <token>`.

Passwords are stored as bcrypt hashes. A failed login gives the same error whether the
email exists or not.

## Quick start

Only Docker and `make` are needed. Nothing to configure:

```sh
make run
```

That one command:

1. creates a git-ignored `.env` with **random** local credentials on the first run (never printed)
2. builds and starts the 4 databases and 4 services
3. creates the tables ([`db/schema/`](db/schema/)) and loads example data ([`db/seed/`](db/seed/))

The API is then at `http://localhost:6006`. Log in as the demo admin:

```sh
curl -X POST localhost:6006/api/login -d '{"email":"librarian@example.com","password":"password123"}'
```

| Command | What it does |
|---|---|
| `make run` / `make up` | build + start everything, wait for the tables, load demo data |
| `make down` | stop everything; the data is kept |
| `make reset` | stop, **delete all data**, then `make up` again |
| `make seed` | load the demo data again (safe to repeat) |
| `make logs` | follow the logs of the four services |
| `make ps` | show container status |
| `make test` | run the unit tests of all four services (in a Go 1.23 container) |

The tables are created from [`db/schema/`](db/schema/) the first time each database volume
starts. See [db/README.md](db/README.md) for the schema, the seed data, and how they relate to
the Go models.

All settings live in `.env` files; see [Environment files](#environment-files-env) below.

### Example data

| Database | Data (from `db/seed/*.sql`) |
|---|---|
| author_mst | 8 authors (ids 1–8) |
| category_mst | 8 categories (ids 1–8) |
| book_mst | 14 books with categories. Book 13 has stock 0 and book 14 has stock 1, for testing borrowing |
| user_mst | `librarian@example.com` (admin), `budi@`, `siti@`, `andi@example.com` (members) |

All demo accounts use the password `password123`. **This is lab data only**; never reuse these
accounts outside a local machine. Running the script again is safe, because existing rows are skipped.
The admin from `ADMIN_EMAIL` is created separately by user-service.

## Environment files (`.env`)

There are five `.env` files. **Which one is used depends on how you start the services.** All of
them are git-ignored, and none is needed for `make run` (it creates the root one itself).

| File | Used when | Read by | Created by |
|---|---|---|---|
| `.env` (repo root) | `make run` / `docker compose` | [`docker-compose.yml`](docker-compose.yml) (`${VAR}`), which passes the values into the containers | `make run`, automatically, with random values |
| `author-service/.env` | `go run .` inside `author-service/` | [`author-service/cmd/server.go`](author-service/cmd/server.go) `loadDotenv()` | you (template below) |
| `category-service/.env` | `go run .` inside `category-service/` | [`category-service/cmd/server.go`](category-service/cmd/server.go) `loadDotenv()` | you |
| `book-service/.env` | `go run .` inside `book-service/` | [`book-service/cmd/server.go`](book-service/cmd/server.go) `loadDotenv()` | you |
| `user-service/.env` | `go run .` inside `user-service/` | [`user-service/cmd/server.go`](user-service/cmd/server.go) `loadDotenv()` | you |

How the values travel:

```
Docker:  .env (root) ──> docker-compose.yml ──> container environment ──> os.Getenv() in the service
Local:   <service>/.env ──> godotenv.Load(".env") in cmd/server.go ──> os.Getenv() in the service
```

In Docker the service `.env` files are **not** used: `.dockerignore` keeps them out of the image,
and the service logs `no .env file found, using environment variables`. Locally, a variable that
is already set in your shell wins over the one in `.env` (godotenv never overwrites).

### Root `.env`, used by `docker-compose.yml`

| Variable | Example | Goes to (in `docker-compose.yml`) | Then read by |
|---|---|---|---|
| `DB_USER` | `library` | `POSTGRES_USER` of all 4 databases, and `DB_USER` of all 4 services | Postgres creates this login; services: `internal/config/postgres.go` |
| `DB_PASSWORD` | *random* | `POSTGRES_PASSWORD` of all 4 databases, and `DB_PASSWORD` of all 4 services | same as above |
| `JWT_SECRET` | *random, ≥ 32 bytes* | `JWT_SECRET` of user-service | `user-service/cmd/server.go` → `internal/auth/jwt.go` (signs and verifies tokens) |
| `JWT_TTL` | `24h` | `JWT_TTL` of user-service | `user-service/cmd/server.go` `jwtTTL()` (token lifetime) |
| `ADMIN_EMAIL` | *optional* | `ADMIN_EMAIL` of user-service | `user-service/cmd/server.go` → `EnsureAdmin` creates this admin at startup |
| `ADMIN_PASSWORD` | *optional* | `ADMIN_PASSWORD` of user-service | same |
| `DB_PORT_AUTHOR` | `4011` (default) | host port of `authordb` (`127.0.0.1` only) | you, e.g. a DB client or `go run` |
| `DB_PORT_CATEGORY` | `4012` (default) | host port of `categorydb` | same |
| `DB_PORT_BOOK` | `4013` (default) | host port of `bookdb` | same |
| `DB_PORT_USER` | `4014` (default) | host port of `userdb` | same |

`make run` writes the first four. Everything else a container needs (`GRPC_PORT`, `IP_PORT`,
`DB_HOST`, `DB_NAME`, `DB_PORT=5432`, `*_GRPC_ADDR`) is fixed inside `docker-compose.yml`
itself, because those values only make sense inside the Docker network.

### Service `.env` files, used by `go run`

To run the services on your machine instead of in Docker, start only the databases and give each
service its own `.env`:

```sh
docker compose up -d authordb categorydb bookdb userdb     # uses the root .env
cd author-service && go run .                              # one terminal per service
```

Comments marked `before:` compare each line with the old setup on `main` / `dev` (before this
branch), where every service ran its own gateway and the databases had their own `db/.env`.

`author-service/.env`
```env
GRPC_PORT=6001          # cmd/server.go: gRPC listen port            (before: same)
DB_HOST=localhost       # internal/config/postgres.go                (before: same)
DB_PORT=4011            # = DB_PORT_AUTHOR in the root .env, host port, NOT 5432
                        #   (before: = DB_PORT_AUTHOR in db/.env)
DB_NAME=author_mst      #                                            (before: same)
DB_USER=YOUR_DB_USER         # must equal DB_USER in the root .env
                             #   (before: had to match the user hardcoded in db/docker-compose.yml)
DB_PASSWORD=YOUR_DB_PASSWORD # must equal DB_PASSWORD in the root .env (before: same, hardcoded)
# IP_PORT=6000          # before: author-service ran its own REST gateway here.
                        #   Now ignored; the only REST port is user-service IP_PORT.
```

`category-service/.env`
```env
GRPC_PORT=6003          # (before: same)
DB_HOST=localhost
DB_PORT=4012            # = DB_PORT_CATEGORY (before: = DB_PORT_CATEGORY in db/.env)
DB_NAME=category_mst
DB_USER=YOUR_DB_USER
DB_PASSWORD=YOUR_DB_PASSWORD
# IP_PORT=6002          # before: own REST gateway. Now ignored.
```

`book-service/.env`
```env
GRPC_PORT=6005          # (before: same)
DB_HOST=localhost
DB_PORT=4013            # = DB_PORT_BOOK (before: = DB_PORT_BOOK in db/.env)
DB_NAME=book_mst
DB_USER=YOUR_DB_USER
DB_PASSWORD=YOUR_DB_PASSWORD
AUTHOR_GRPC_ADDR=localhost:6001     # cmd/server.go dialGRPC: = GRPC_PORT of author-service
                                    #   (before: did not exist, book-service called no other service)
CATEGORY_GRPC_ADDR=localhost:6003   # = GRPC_PORT of category-service (before: did not exist)
# IP_PORT=6004          # before: own REST gateway. Now ignored.
```

`user-service/.env` (new: user-service and `userdb` did not exist before)
```env
IP_PORT=6006            # public REST gateway port (= {{lm-url}} in Postman)
                        #   (before: each service had its own IP_PORT 6000/6002/6004)
GRPC_PORT=6007          # internal gRPC port of user-service
DB_HOST=localhost
DB_PORT=4014            # = DB_PORT_USER (before: userdb was commented out)
DB_NAME=user_mst
DB_USER=YOUR_DB_USER
DB_PASSWORD=YOUR_DB_PASSWORD
AUTHOR_GRPC_ADDR=localhost:6001     # gateway routes /api/author*   here
CATEGORY_GRPC_ADDR=localhost:6003   # gateway routes /api/categor*  here
BOOK_GRPC_ADDR=localhost:6005       # gateway routes /api/book*     here
JWT_SECRET=YOUR_RANDOM_SECRET_AT_LEAST_32_BYTES   # e.g. openssl rand -hex 32 (before: no auth)
JWT_TTL=24h             # optional, see below
ADMIN_EMAIL=            # optional, see below
ADMIN_PASSWORD=         # optional, 8-72 characters
```

Running locally needs Go 1.23+.

### Optional variables

Leave these empty (or remove the line) and the service still starts:

| Variable | Service | If empty | Optional case |
|---|---|---|---|
| `JWT_TTL` | user-service | tokens last `24h` | `JWT_TTL=30m` for short tokens while testing expiry; `JWT_TTL=168h` for a week. Any Go duration (`90s`, `2h45m`); an invalid value stops the service at startup |
| `ADMIN_EMAIL` | user-service | no admin is created; register users through `POST /api/register` | Set it with `ADMIN_PASSWORD` to get an admin at startup, e.g. on a fresh `make reset` database |
| `ADMIN_PASSWORD` | user-service | only read when `ADMIN_EMAIL` is set | Must be 8-72 characters, otherwise startup fails with `admin password must be 8-72 characters` |
| `DB_PORT_AUTHOR` … `DB_PORT_USER` | root `.env` | defaults `4011`-`4014` | Change one when the port is already taken on your machine, then use the same value as `DB_PORT` in that service's `.env` |
| `IP_PORT` | author / category / book | ignored | Leftover from the old setup, safe to keep or delete |

Optional setups:

- **Mix Docker and `go run`**: run everything with `make run`, then `docker compose stop author-service`
  and start it with `go run .`. Its `.env` must use the root `DB_USER` / `DB_PASSWORD` and
  `DB_PORT=4011`. Other containers still dial `author-service:6001` inside Docker, so only
  standalone testing of that service works this way.
- **Only one service**: author-service and category-service need nothing but their own database.
  book-service also needs author- and category-service running; user-service needs all three.
- **Shell instead of `.env`**: `DB_PORT=4111 go run .` overrides the file for one run, because a
  variable already set in the shell wins.

| | Before (`main` / `dev`) | Now (this branch) |
|---|---|---|
| Database settings | `db/.env` + `db/docker-compose.yml` | root `.env` + root `docker-compose.yml` |

### How the files connect

```
root .env                          service .env files
─────────                          ──────────────────
DB_USER, DB_PASSWORD  ═══ same ═══ DB_USER, DB_PASSWORD     (in all four)
DB_PORT_AUTHOR=4011   ═══ same ═══ author-service   DB_PORT
DB_PORT_CATEGORY=4012 ═══ same ═══ category-service DB_PORT
DB_PORT_BOOK=4013     ═══ same ═══ book-service     DB_PORT
DB_PORT_USER=4014     ═══ same ═══ user-service     DB_PORT

author-service   GRPC_PORT=6001 ══> book-service AUTHOR_GRPC_ADDR,   user-service AUTHOR_GRPC_ADDR
category-service GRPC_PORT=6003 ══> book-service CATEGORY_GRPC_ADDR, user-service CATEGORY_GRPC_ADDR
book-service     GRPC_PORT=6005 ══>                                  user-service BOOK_GRPC_ADDR
user-service     IP_PORT=6006   ══> Postman {{lm-url}} = http://localhost:6006
```

Things that commonly go wrong:

- **`password authentication failed`**: the service's `DB_USER` / `DB_PASSWORD` don't match the
  root `.env`. The databases were created with the root values.
- **Changed `DB_PASSWORD` in the root `.env`, now nothing connects**: Postgres saved the password
  inside the volume on the first start and ignores later changes. Run `make reset` (**deletes all
  data**) to recreate the databases with the new password.
- **`connection refused` on port 5432**: locally, `DB_PORT` is the *host* port (4011–4014).
  5432 is only valid inside Docker.
- **`JWT config: JWT secret must be at least 32 bytes`**: `JWT_SECRET` is too short or missing.
- **Tokens stop working after a restart**: `JWT_SECRET` changed, which invalidates all tokens.
  Log in again.

Older copies of `author-service/.env`, `category-service/.env` and `book-service/.env` may still
contain `IP_PORT`. It is no longer read by those services and can be removed. Those three files
were committed to git in the past; stop tracking them with
`git rm --cached author-service/.env category-service/.env book-service/.env`.

## REST API — `http://localhost:6006`

**Postman:** import [`postman/library-management.postman_collection.json`](postman/library-management.postman_collection.json).
Run *Auth → Login (admin)* first; it saves the JWT into `{{lm-token}}`. The base URL is `{{lm-url}}`.

The OpenAPI spec is served at `GET /openapi/library.swagger.json`. Liveness check: `GET /healthz`.

Errors look like `{"code": <gRPC code>, "message": "...", "details": []}`. HTTP status codes:

| Status | Meaning |
|--------|---------|
| `400`  | invalid input, or not enough stock |
| `401`  | missing, invalid or expired token |
| `403`  | admin role required |
| `404`  | not found |
| `409`  | email already registered |
| `503`  | a backend service is down |
| `500`  | anything else, with a generic message |

List endpoints are server streams: they return one `{"result": {...}}` JSON object per line.

### Users

| Method | Path            | Auth   | Body                                |
|--------|-----------------|--------|-------------------------------------|
| POST   | `/api/register` | public | `{"username", "email", "password"}` |
| POST   | `/api/login`    | public | `{"email", "password"}` → `{"token", "expiresAt", "user"}` |
| GET    | `/api/me`       | any    |                                     |

### Authors

| Method | Path               | Auth  | Body                       |
|--------|--------------------|-------|----------------------------|
| POST   | `/api/author`      | admin | `{"name", "biography"}`    |
| GET    | `/api/authors`     | any   |                            |
| GET    | `/api/author/{id}` | any   |                            |
| PUT    | `/api/author/{id}` | admin | any of `name`, `biography` |
| DELETE | `/api/author/{id}` | admin |                            |

### Categories

| Method | Path                 | Auth  | Body                         |
|--------|----------------------|-------|------------------------------|
| POST   | `/api/category`      | admin | `{"name", "description"}`    |
| GET    | `/api/categories`    | any   |                              |
| GET    | `/api/category/{id}` | any   |                              |
| PUT    | `/api/category/{id}` | admin | any of `name`, `description` |
| DELETE | `/api/category/{id}` | admin |                              |

### Books

| Method | Path                   | Auth  | Body                                                                |
|--------|------------------------|-------|---------------------------------------------------------------------|
| POST   | `/api/book`            | admin | `{"name", "description", "authorId", "stock", "categoryIds": [..]}` |
| GET    | `/api/books`           | any   |                                                                     |
| GET    | `/api/book/{id}`       | any   |                                                                     |
| PUT    | `/api/book/{id}`       | admin | any of `name`, `description`, `authorId`, `categoryIds`             |
| POST   | `/api/book/{id}/stock` | admin | `{"delta": -1}` to take a copy, `{"delta": 1}` to return one        |
| DELETE | `/api/book/{id}`       | admin |                                                                     |

A book response looks like this. `authorName` and `categories` are filled in by the server from
author-service and category-service:

```json
{"id": 1, "name": "Sample Book", "description": "", "authorId": 1, "authorName": "Jane Doe",
 "stock": 5, "categories": [{"id": 1, "name": "Fiction"}]}
```

A non-empty `categoryIds` on update replaces the book's categories.

A stock change runs as one conditional `UPDATE ... WHERE stock + delta >= 0`, so concurrent
borrows can never take stock below zero. A `CHECK (stock >= 0)` constraint backs this up.

Example:

```sh
TOKEN=$(curl -s -X POST localhost:6006/api/login \
  -d '{"email":"YOUR_ADMIN_EMAIL","password":"YOUR_ADMIN_PASSWORD"}' | jq -r .token)
AUTH="Authorization: Bearer $TOKEN"

curl -X POST localhost:6006/api/author   -H "$AUTH" -d '{"name":"Jane Doe","biography":"Sample"}'
curl -X POST localhost:6006/api/category -H "$AUTH" -d '{"name":"Fiction","description":"Sample"}'
curl -X POST localhost:6006/api/book     -H "$AUTH" -d '{"name":"Sample Book","authorId":1,"stock":5,"categoryIds":[1]}'
curl -X POST localhost:6006/api/book/1/stock -H "$AUTH" -d '{"delta":-1}'
curl localhost:6006/api/books -H "$AUTH"
```

## Development

```sh
make proto      # regenerate code after editing a .proto (in each service)
make clients    # book-service: regenerate author/category gRPC clients
make gateways   # user-service: regenerate REST handlers for author/category/book
make openapi    # user-service: regenerate openapi/library.swagger.json
make test       # unit tests
```

After changing a `.proto` in author, category or book, also run `make gateways openapi` in
user-service, plus `make clients` in book-service if author or category changed.

Code generation needs `protoc` with `protoc-gen-go`, `protoc-gen-go-grpc`,
`protoc-gen-grpc-gateway` and `protoc-gen-openapiv2`.

The book repository has integration tests, including a concurrent-borrow race test. They run
against a real database when `BOOK_TEST_DSN` is set:

```sh
BOOK_TEST_DSN="host=localhost port=4013 user=YOUR_DB_USER password=YOUR_DB_PASSWORD dbname=book_mst sslmode=disable" \
  go test -race ./internal/repository/
```
